# MVP-06 publication operator guide

## Before enabling Managed KB

Back up PostgreSQL and the local immutable object store, then apply migrations `0019` through `0022`. The migrations add generation reconciliation state, artifact mapping/status, and the PostgreSQL pin guard for plan-backed summaries. Keep the decision ledger, source snapshots, and old generation mappings during rollback. The production runtime needs a durable POSIX local object store for curated staging; the source root remains read-only.

Keep `PROPOSAL_PUBLICATION_BACKEND=local` for offline work. For a configured private AWS deployment, use `PROPOSAL_PUBLICATION_BACKEND=managed_kb`, `AWS_REGION`, `PROPOSAL_CURATED_BUCKET`, `BEDROCK_KNOWLEDGE_BASE_ID`, and `BEDROCK_DATA_SOURCE_ID`. The S3 data source must be `AVAILABLE` and use that bucket with exactly the `curated/` inclusion prefix from `publication_s3_prefix`. Configure private bucket access and scoped worker, KB service, and retrieval IAM roles outside this PR. Do not point the KB at an original snapshot prefix or direct SharePoint source. Keep unrelated data out of the curated bucket prefix. No live call is needed to use the local adapter.

Use the normal authenticated collection page to request publication. For a plan-backed proposal, the request stages a new generation; the worker uploads and polls it. Run `python scripts/manage.py worker` as the single publication worker. The collection page shows the latest generation's pending/failed state and the last successful active revision. A local backend stages, verifies, and activates immediately. A failed Managed KB generation can be retried with `python scripts/manage.py reconcile_publication <generation-uuid>` after addressing the cause. The command is idempotent for immutable S3 objects. It retains the prior successful generation until a replacement is fully verified, although a changed or excluded source may already make the old passages ineligible.

For a fictional end-to-end rehearsal against PostgreSQL, run `python scripts/manage.py fixture_publication`. It invokes the existing read-only MVP-05b fixture source sync, extraction, and classification, then publishes the one mock-policy eligible passage. Its output prints proposal/generation IDs, state, and artifact count. Inspect actual stored bytes and the review queue. The source fixture contains a sensitivity exclusion and unresolved scientific/status/voice issues; those passages do not publish. Do not use this fixture command in production.

## Exclusion, deletion, and recovery

A human exclusion or a changed/retired source invalidates affected application membership immediately. Search, pins, packet reuse, and drafting recheck current eligibility even if the old KB object remains indexed. For retired generations, `python scripts/manage.py reconcile_publication <generation-uuid> --delete` removes the S3 text and metadata sidecars, starts a sync, and checks exact `NOT_FOUND` statuses. Repeat the command while deletion is pending; a failed deletion job can be retried. Keep the application gate active throughout lag. Do not delete a generation still active or required for an eligible rollback.

Before exposing a restored database, set `PROPOSAL_PUBLICATION_HOLD=true`. Restore the matching immutable local/S3 objects and decision audit, compare the recovery point with source/decision changes after it, and reconcile any newer exclusions before clearing the hold. Unknown KB results are rejected by mapping, but a database restored before a later exclusion cannot infer that exclusion by itself. Keep the hold until that gap is resolved. Then re-stage or reconcile current generations. To restore a retired, still eligible generation, run `python scripts/manage.py reconcile_publication <generation-uuid> --restore`; this requires exact current plan and document verification. If any check fails, keep the passage unavailable. Historical citations remain readable and marked withdrawn.

The live MVP-08 verification must prove bucket privacy, source-prefix isolation, exact metadata and citation round-trip, completion/partial/failure statuses, S3 deletion propagation, retry behavior, costs, and the restore hold. Record KB/data source identifiers, job IDs, region, object counts, and sanitized errors privately; never paste source text, credentials, or model prompts into public review.
